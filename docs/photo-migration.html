Outside the lab · data migration · 2026

I moved a 1.74 TB photo drive into iCloud. No batch counted until its checks passed.

The drive is a 2012 Seagate that holds my 2014–2017 photos and video: 945 GiB in four old iPhoto libraries and loose folders, plus a Time Machine backup that turned out to hold photos found nowhere else. The work uses the capture discipline from district.local. Claude writes each script, and every claim points at a captured output file. I ran the scripts from Terminal.app until 2026-10-14; Claude's shell now runs them with Full Disk Access.

The pipeline

Four independent checks cover the path from drive to iCloud

Files leave the drive over USB, pass through the Mac mini's internal disk, and upload to iCloud Photos. Photos removes a local original after it reaches iCloud, so the internal disk is a buffer. Each check must pass before a batch counts as done.

Where it stands

Every batch is closed, the Time Machine backup included. Open decisions remain.

Done means every media file is in Photos or explained: a byte copy of an asset already in, a file out of scope, or a recorded decision. Asset counts are each album's count at its latest capture; they exclude non-key burst frames.

The tech

osxphotos and Photos.app import the files. My own scripts check their work.

The importer's own counts proved unreliable in the first week, so every number it reports is checked by a second tool.

Hardware and services

Seagate drive
Backup Plus Desk, 2 TB, USB, HFS+, from 2012. The USB bridge blocks SMART, so the drive's health is unknown. It is read in place and was never imaged: the Mac has one free port.
Mac mini
macOS 26, then 27.0.1 from 2026-10-14. About 460 GiB of internal disk. Every original passes through this disk before upload. Free space limits the whole run.
iCloud Photos
The destination, through Photos.app with Optimize Mac Storage on. Photos removes a local original after it is in iCloud.
cloudphotod
The macOS upload service. Its log shows low-disk refusals and download events.
External SSD
Took 25 GB of Lightroom renders and an iMovie backup image to free local space. It is not on the photo path.

The import, damaged-video, library-check, Live Photo and round-trip scripts each have a fixture suite with deliberate mutants. A broken check fails its own test before it runs on real data.

How a batch runs

One folder, cut into chunks that check themselves and wait for the upload

  1. Probe the videos. mov-atoms-batch.sh reads every clip in the folder, with four known control files. Clips with no media data go on a known-bad list. A second scan reads every Live Photo content ID.
  2. Map the folder. One dry run of the whole folder records how osxphotos groups files. Live Photo videos are held back by full path, to be attached after their stills.
  3. Predict every chunk. The plan comes from the batch's own fingerprints. Each chunk's imported and skipped counts are committed to git before anything runs.
  4. Import in chunks. Each chunk gets its own dry run, then the import, then a reconcile. Any error stops the run, and it resumes where it stopped.
  5. Pace to the upload. Before each chunk, the album's not-in-iCloud count must be at or below what the last chunk imported. Below 30 GiB free, the run switches to small serial steps.
  6. Attach the Live Photo videos. A second pass joins each held-back video to its still. The inventories before and after must show every attach and no new asset.
  7. Drain. After the last chunk, the run waits until nothing in the album is still waiting to upload.
  8. Watch. chunk-watch.sh compares each finished chunk with its predicted row. sync-kick-watch.sh restarts a stalled upload. caffeinate keeps the Mac awake.
  9. Close the folder. A close script fingerprints every file again, takes a fresh library inventory, and runs the library check, the reverse pass and the cloud state.

The pacing exists because import runs at about 20 GiB/h and upload at about 3.95 GB/h. When the import outran the upload, the disk filled with originals Photos could not remove, and the upload stopped.

The four checks

A batch is done when four independent checks pass. The importer's own count is not one of them.

01
Count

Imported plus skipped must equal the chunk's own dry run, with 0 errors.

The first version compared the library's growth with the importer's claim. That comparison agrees with the importer by construction, and it cannot see a lost file.

Why it existsOn 2026-09-21 the old comparison reported a clean batch. That batch had lost 5,874 groups, and osxphotos had exited 0.

02
Upload

The album's count of assets not yet in iCloud must reach 0.

osxphotos reads the upload flag for each asset. The run waits for the drain, so "done" means uploaded.

03
Fingerprint

Every source file must match a live Photos asset by Photos' own fingerprint.

Each file lands in one class: LIVE, NOT-MEDIA, KNOWN-BAD, TRASH-ONLY or UNMATCHED. TRASH-ONLY and UNMATCHED must be 0. A Live Photo video stored inside its still's asset matches by content ID instead (LIVE-BY-ID). A reverse pass looks for album assets with no source file. For 2015/CRS: 10,844 media files LIVE, 0 unmatched, 0 strays.

Why it existsThis check found all three duplicate-skipping losses listed below. The importer reported 0 errors in each run.

04
Bytes

A seeded sample of evicted originals is downloaded back and compared with the drive by SHA-256.

The sample and its seed are committed before any download. 2015/CRS: 62 of 62 identical, across CR2, NEF, JPG, MOV and PNG. 2017/ip2017: 63 of 63 non-Live originals identical.

Why it existsPhotos marked steps "in iCloud" after about 12–17% of their bytes had left the Mac. The cause is not established, so the flag is not proof.

  • The expected results are written down before a check runs.
  • Every probe includes known control files. A control that misses stops the run.
  • A check is never relaxed after its result is seen.

A separate read-only pass on 2026-10-15 re-checked the whole result after every batch closed. Two review agents audited its scripts first and found 3 blockers and 7 major defects, all fixed before anything ran.

  • Cross-hash: 200 Seagate files drawn at random with a committed seed. 74 byte-identical in Photos, 0 mismatches. 124 skipped because their originals are not on this Mac; 2014–2017 had 0 checkable files. 2 missing by recorded decision.
  • Reconciliation: 0 listed source files unaccounted for in all 8 strata. The first run's 156 all traced to recorded decisions.
  • Ledger: FAIL. 361 corrections and 38 questions all defined; 4 cited files do not exist. One of the four is a path Claude wrote wrong.
  • Provenance: the rescued company archive and the migration material on the SSD overlap in 0 files.
  • Health: BLOCKED. SMART is still unreadable through the USB bridge.

What the checks caught

Thirty problems. Four lose files without an error, and two were this page's own claims.

All four silent losses were caught, and every affected file was recovered. A wrong published claim is retired here, not edited away. Newest first.

What remains

The drive is wiped after every folder passes and the backup decision is made

  • Decide on the 32 encrypted backup files. They need that backup's password.
  • Run the round trip for Live Photos, and for batches whose originals are still local.
  • Decide whether XMP sidecars, PDFs and other documents are in scope. They do not reach Photos.
  • Decide whether to import the 2 locked JPEGs from unlocked copies.
  • Back up the evidence repository. It has no remote.
  • Wipe and retire the drive. Every batch is closed; the decision is mine to make.
