# Hybrid identity, part 1 — UPN baseline and the connectivity chain that had to exist before any of it could start

## What I set out to do

Every prior exercise in this series has been on-prem only. SC-300 (Microsoft Identity and Access Administrator) is roughly 70%+ Entra ID — Conditional Access, PIM, Identity Protection, entitlement management — none of which district.local can teach standing alone. The bridge is hybrid identity: sync DC01 into an Entra tenant with Entra Connect. This exercise is the groundwork that has to happen before Connect can run at all: baseline the forest's UPN state (Connect rewrites `userPrincipalName` on export if the source domain isn't routable, and `district.local` isn't), and confirm DC01 can actually reach Microsoft's endpoints over the network.

It did not stay a baseline exercise. The reachability check failed immediately, and tracking down why turned into the bulk of this report.

## The setup

Same DC01 (VM 100, `district.local`), same capture path (`qm guest exec` from the Proxmox host — DC01 has no remoting). Pre-flight run first, per the skill's standing step added after the prior crash exercise: thin pool at 77.49% (holding steady since the prune, well under the 85% stop-threshold), 9.9Gi host memory available, VM 100 confirmed running before anything touched it. Full readout in `evidence/proxmox-preflight-headroom.txt`.

One piece of state came from Raymond directly, not a query: a screenshot of the Entra admin center showing an existing tenant (`raytakosharkygmail.onmicrosoft.com`, Entra Free, tenant ID `e0b13496-83d1-4721-8bf9-f965f676106f`), last touched in October. Per the capture contract, a screenshot is not evidence — it isn't filed under `evidence/`, and nothing in this report cites it as a captured fact. It answers one open question (a tenant exists) but everything about its current state is unverified until pulled through a real API call.

## What I did

Five baseline queries, all `qm guest exec 100 --timeout 30/60 -- powershell.exe -Command "..."`, all exit code `0` except the reachability test discussed below:

1. `Get-ADForest | Select-Object Name,ForestMode,UPNSuffixes,DomainNamingMaster,SchemaMaster`
2. `Get-ADDomain | Select-Object Name,DNSRoot,NetBIOSName,DomainMode,PDCEmulator`
3. `Get-ADUser -Filter * -Properties UserPrincipalName,mail,proxyAddresses`
4. `Test-NetConnection -ComputerName login.microsoftonline.com -Port 443`
5. Four more diagnostic rounds chasing why (4) failed — detailed in "What broke, and why," since the failure and its diagnosis *is* most of this exercise's content.

Raymond's actual answer went further than either option: *"business is kaput, no need keep it separate, lets just run it for testing, we got a month or so before i consider renewing, so what you consider is best recommended for our lab."* Given the domain's registration itself is uncertain past roughly a month, I recommended — and this is my call, stated as such, not something Raymond specified directly — stamping real UPNs on the tenant's permanent `onmicrosoft.com` suffix instead, while still verifying `districtsafetyphoto.com` in the tenant as its own small, separately-captured exercise before it potentially lapses. Reasoning: an identity foundation this series builds on top of shouldn't be anchored to a namespace with a known expiration date, but the domain-verification mechanics (TXT record, Entra's check) are real SC-300 content that disappears the moment the domain does, so capturing it now costs little and loses nothing later. **Not yet executed** — this is a decision on record, not a completed action.

## What the box said

**Forest UPN suffixes** (`evidence/forest-upn-suffixes-baseline.json`, exit code `0`) — `UPNSuffixes: []`, empty. **Captured.** Confirms the predicted blocker directly: no alternative suffix exists, every account is `@district.local`, and an unmodified Entra Connect sync would rewrite every one of them to `@<tenant>.onmicrosoft.com` on export.

**Forest and domain functional level** (`evidence/forest-upn-suffixes-baseline.json`, `evidence/domain-identity-baseline.json`, both exit code `0`) — `ForestMode: 7` / `DomainMode: 7`, decoding to `Windows2016Forest` / `Windows2016Domain` — **interpretation, not printed as text**, same labeling convention as the ADWS status decode in an earlier exercise. Relevant beyond this report: 2016 FFL is what the PAM optional feature (time-bound group membership, the on-prem PIM analogue flagged in an earlier exercise's open questions) requires, so that path stays available whenever it's picked up.

**Every user's UPN state** (`evidence/all-users-upn-state-baseline.json`, exit code `0`) — 13 accounts, matching the count already confirmed in the prior exercise. **Captured**, and one finding stands out: `bhound` has `UserPrincipalName: null`. Every other user-created account (everything except the three AD built-ins — `Administrator`, `Guest`, `krbtgt`, which are null by design) has a `@district.local` UPN. `bhound` is the sole exception. **Entra Connect requires `userPrincipalName` to export an object at all** — an account without one doesn't sync, it errors. This is a real data-quality defect, found by reading the baseline before Connect ever ran, rather than as a confusing sync failure afterward.

**Reachability, attempt 1 — failed at DNS** (`evidence/dc01-entra-endpoint-reachability-failed.json`, exit code `0` — **not proof of success on this command**, see the note below) — `Test-NetConnection -ComputerName login.microsoftonline.com -Port 443` returned `TcpTestSucceeded: false, PingSucceeded: false`, with `WARNING: Name resolution of login.microsoftonline.com failed`. **Captured**, and this is the finding that turned a baseline exercise into an investigation.

**A convention break, worth stating plainly:** every prior exercise in this series treats exit code `0` as trustworthy and anything nonzero as the signal to look closer. `Test-NetConnection` breaks that rule — it returns `0` on a connectivity *test that failed*, because the cmdlet itself ran successfully; the failure is reported in the payload (`TcpTestSucceeded`/`PingSucceeded`) and a `WARNING:` stream line, not the exit code. Applying the series' own convention mechanically here would have missed the failure. Filed as a deliberate counterexample, not smoothed over.

**Diagnosis, round 2 — the wrong layer.** My working hypothesis (stated to Raymond before testing) was "pfSense egress is probably fine, DC01's DNS forwarder is broken." `Get-DnsServerForwarder` (`evidence/dc01-dns-forwarder-ipv6-dead.json`) showed a forwarder *is* configured — a single IPv6 address, `2600:6c50:5940:587:ea9f:80ff:fe81:22f7`, on a lab network that is IPv4-only end to end. That's consistent with the hypothesis. But `Test-NetConnection -ComputerName 1.1.1.1 -Port 443` — a raw-IP test that bypasses DNS resolution entirely — also failed (`evidence/dc01-egress-to-1111-failed-host-unreachable.json`), with `PingSucceeded: false, status: DestinationHostUnreachable`. That result is typically generated by the sender's own routing stack, not a remote firewall rejection, and it directly falsified "egress is fine."

**Diagnosis, round 3 — root cause.** `Get-NetIPConfiguration` (`evidence/dc01-net-ip-configuration-full.json`, filed as an extraction — see the file's own note on trimming CIM metadata noise) showed DC01's default route pointing to next-hop `192.168.1.1`. That address is the **home network's** gateway (`vmbr0`, per the inherited BloodHound write-up), not `10.0.0.1` — pfSense's LAN interface on the `10.0.0.0/24` bridge DC01 actually lives on. `192.168.1.1` isn't reachable from `10.0.0.10/24` at all; Windows can't ARP across subnets, so every off-subnet packet from DC01 had nowhere to go, independent of pfSense's firewall rules entirely. `Test-Connection -ComputerName 10.0.0.1` (`evidence/dc01-gateway-to-101-ping-success.json`) succeeded instantly, confirming pfSense's LAN side was never the problem — the diode rule, the thing I expected to find blocking this, was never involved at any point in this investigation.

### Remediation: two independent fixes, both verified

**Fix 1 — default gateway.** `Remove-NetRoute -DestinationPrefix '0.0.0.0/0' -NextHop '192.168.1.1'` then `New-NetRoute -DestinationPrefix '0.0.0.0/0' -NextHop '10.0.0.1' -InterfaceAlias 'Ethernet'` (`evidence/dc01-gateway-removal-old-route.json`, `evidence/dc01-gateway-new-route-added.json`, both exit code `0`). Verified via `Get-NetRoute` showing `NextHop: 10.0.0.1`, and `Test-NetConnection -ComputerName 1.1.1.1 -Port 443` now returning `TcpTestSucceeded: true` (`evidence/dc01-egress-1111-success-after-gateway-fix.json`) — DC01's first working raw egress in this exercise. `PingSucceeded` stayed `false` on the same test; unexplained, not chased, doesn't block anything downstream since TCP/443 is what actually matters for Connect/Graph traffic.

**A hypothesis that didn't survive contact:** I expected the gateway fix alone might restore name resolution too, since the forwarder config showed `UseRootHint: true` (fall back to public root servers if forwarders fail). It didn't — `Resolve-DnsName` still returned `RCODE_SERVER_FAILURE` (`evidence/dc01-dns-still-fails-after-gateway-fix.json`) after the gateway was already fixed. The dead IPv6 forwarder was an active blocker, not something silently bypassed.

**Fix 2 — DNS forwarder.** `Set-DnsServerForwarder -IPAddress 1.1.1.1,8.8.8.8` (`evidence/dc01-forwarder-replaced-ipv4.json`, filed as an extraction, same CIM-noise trimming as the earlier forwarder capture). `1.1.1.1` was picked because it was already confirmed TCP-reachable from this exact box in Fix 1's verification, not a fresh guess.

**Full verification, closing the loop on the same target the exercise opened with:** `Resolve-DnsName -Name login.microsoftonline.com -Type A` (`evidence/dc01-dns-resolution-restored.json`) now resolves through its real CNAME chain (`login.mso.msidentity.com` → `ak.privatelink.msidentity.com` → `www.tm.a.prd.aadg.akadns.net`) to eight live Microsoft/Akamai IPv4 addresses. **Captured**, filed with one paste-contamination note: the raw output had the resolved hostname wrapped in markdown link syntax six times over, which `Resolve-DnsName`'s JSON serializer has no mechanism to produce — treated as noise introduced somewhere in the paste pipeline, not box output, and stripped from the filed evidence with the substitution stated plainly in `evidence/evidence-log.md`.

### Tenant-side capture: the Global Admin identity is an MSA, not a directory account

The remaining open item — verifying the tenant's actual state rather than trusting the October screenshot — turned into the largest single finding in this exercise. Capture path for this section is Graph Explorer rather than `qm guest exec`, run by Raymond and pasted back with the same discipline.

**A UI mixup cost the first three attempts.** Graph Explorer has two separate text areas: the actual query URL field next to the `v1.0` dropdown, and a large "Request Body" panel below it (for POST/PATCH payloads, ignored on GET). The first three pasted results were all the identical default `GET /me` sample query, because the intended query text had gone into the Request Body panel while the URL field sat unchanged. Caught via a screenshot; not a mistake worth hiding, since it's exactly the kind of "looks like it ran, didn't" gap this whole series is built to catch.

**Finding: the tenant's Global Administrator identity is a Microsoft Account (MSA), not a native Entra work/school account.** Once the URL field was actually being used, all four target queries — `GET /organization`, `GET /directoryRoles?$filter=displayName eq 'Global Administrator'`, `GET /domains`, `GET /users?$select=...` — failed with the identical error: `"This API is not supported for MSA accounts (no addressUrl for Microsoft.DirectoryServices,False)."` Four independent calls, four distinct `request-id` values (ruling out a cached repeat), same message every time. **Captured**, and this is a blanket restriction across basic directory reads, not something specific to one endpoint.

This also resolved an anomaly flagged and left open two exchanges earlier: the very first `GET /me` response (before the URL-field mixup was caught) showed `"id": "27701766a4468e98"` — 16 hex characters, no dashes. Real Entra object IDs are always full GUIDs. At the time this was flagged as possibly a paste-truncation artifact and left unresolved. It wasn't one — a malformed, dash-less ID in this shape is the signature of an MSA identity being represented in a directory context it doesn't actually belong to, and the explicit `BadRequest` naming "MSA accounts" directly confirms what the malformed ID had already hinted at.

**Why this outranks a typical error:** the October screenshot showed this identity holding the tenant's sole Global Administrator role, with no visible break-glass account — already flagged as an open question before this exercise started. An MSA-backed Global Admin is a materially more fragile version of that same problem. It isn't just "one admin, no backup" — it's the tenant's top role sitting on an account type that Microsoft's own Graph API partially refuses to treat as a real directory principal, demonstrated directly rather than inferred from documentation.

**One failure had a different, worse shape, and it didn't reproduce.** `/users`'s first attempt came back as a `200`-shaped envelope (`@odata.context` plus a `value` array — the normal signature of success) whose sole array element was itself a buried error: `"Invalid response. Expected list response must have value property"` — a message that contradicts itself, since the response does have a `value` property. That reads as a downstream directory-services failure getting incorrectly wrapped by a Graph gateway layer rather than surfaced honestly. Asked directly what the HTTP status banner showed for that attempt, Raymond re-ran the query instead of checking — a fair, understandable reflex — and the second, identical call came back as a clean `400` with the standard MSA message. The malformed shape is filed as a real, captured event; whether it's reproducible is not established, and the specific banner-status question was never actually answered. Logged as a genuine gap rather than assumed resolved by the retry.

### Remediation: break-glass Global Administrator created

`breakglass@raytakosharkygmail.onmicrosoft.com` created cloud-only, on the tenant's own suffix, via the Entra admin center UI directly (not Graph). Two verifications, both run by Raymond as this new account:

**`GET /me`** (`evidence/graph-me-breakglass-account-clean.json`) — clean `200`, `id: de938dc8-feb7-4140-9a01-8e32649b8fd6`. **Captured**, and this is the direct, clean contrast to the MSA finding above: a proper 36-character dashed GUID against the MSA identity's malformed 16-character `27701766a4468e98`, same tenant, same query. The account behaves as a normal directory principal.

**`GET /me/memberOf`** (`evidence/breakglass-global-admin-role-confirmed.json`) — one object, `roleTemplateId: 62e90394-69f5-4237-9190-012177145e10`. **Captured** for the raw ID; the decode to "this is Global Administrator" is **interpretation** — that template ID is Microsoft's own fixed, documented value for the built-in role, stable across every tenant, not something derived from this session's captures, same labeling convention as the forest/domain mode decodes earlier. One loose end: the object's `displayName` came back `null` rather than the expected `"Global Administrator"` string — plausibly a freshly-instantiated built-in role object not yet carrying its display metadata, but that's inference, not confirmed.

**MFA registration: promoted from Recalled to Captured.** `GET /me/authentication/methods` first failed with `accessDenied` (`evidence/breakglass-mfa-check-scope-denied.json`) — a Graph Explorer consent-scope gap, a distinctly different error from every MSA failure in this exercise and correctly identified as such rather than conflated with them. After consenting to `UserAuthenticationMethod.Read`, the retry (`evidence/breakglass-mfa-confirmed.json`) returned two registered methods: a password, and a Microsoft Authenticator app tied to an iPhone (`deviceTag: SoftwareTokenActivated`). Raymond's earlier statement is now backed by a real API response rather than resting on testimony alone.

## What broke, and why

Two independent, unrelated misconfigurations were both present on DC01 simultaneously, and both had to be found and fixed before anything downstream — Entra Connect, the UPN work, all of it — could even be attempted. Neither was the diode rule. My own prediction, stated to Raymond before any command ran ("expect the firewall to block it"), was wrong on both counts: wrong about which layer was broken, and wrong twice more about what fixing the first thing would or wouldn't also fix.

That's worth sitting with rather than glossing over, because it's the same shape of error the constrained-admin-path exercise flagged: precise data can make a wrong hypothesis feel more confident, not less. Round 2's data (a genuinely dead IPv6 forwarder) fit my prediction well enough that it would have been easy to stop there, fix the forwarder, and report "fixed the DNS misconfiguration" — while DC01 still had zero working egress underneath it, because the gateway was also broken. Testing the *bypass* (`1.1.1.1` instead of a hostname) is what surfaced the second, more fundamental problem. The lesson isn't "check more things" in the abstract — it's that a hypothesis confirmed by one piece of evidence still needs a test designed to falsify it, not just corroborate it.

The `Test-NetConnection` exit-code convention break is the other genuine "what broke": this series has leaned on exit code `0` as the trustworthy signal since exercise 1, and this is the first command where that rule would have actively misled if applied without reading the payload.

## What I'd do differently

Run the bypass test (`1.1.1.1`, no DNS involved) *before* the hostname test, not after it failed. It's a cheaper, more isolating check, and it would have ruled out "DNS is the whole problem" in the first round instead of the third — I only reached the gateway diagnosis because the DNS-focused fix didn't fully explain the symptom, and that took an extra round to notice.

I'd also front-load a general routing sanity check (`Get-NetRoute -DestinationPrefix 0.0.0.0/0`, one line) into the standard pre-flight, alongside the thin-pool/memory check already there. This exercise's whole detour exists because that single fact wasn't checked until round 3 of an investigation that started in round 1.

- **`bhound`'s missing UPN needs a decision, not just a note.** Give it a UPN so it can sync, exclude it from the sync scope entirely, or decide it shouldn't exist at all (it's already flagged in the prior exercise as a stale BloodHound-collector account past its stated purpose) — Raymond's call.
- **The `districtsafetyphoto.com` domain-verification exercise is planned, not done.** Per the consultation above: verify it in the tenant before the ~month-long renewal window closes, capture the TXT-record flow as evidence, and do not stamp any user UPNs on it.
- **The UPN re-stamp itself (`district.local` → `onmicrosoft.com` suffix, applied per-user) has not been run.** This is the highest-blast-radius single action remaining in this whole hybrid-identity effort — every real user account gets touched — and per this series' established pattern it gets a fresh snapshot and Raymond's explicit sign-off on the exact command before it runs, same as the `sysadmin` removal.
- **Partially resolved: a break-glass Global Administrator now exists, cloud-only, verified as a clean directory principal.** `breakglass@raytakosharkygmail.onmicrosoft.com`, `GET /me` and `/me/memberOf` both confirm it — see Remediation. What's not resolved: **the original MSA identity is still the tenant's other Global Administrator, untouched.** Creating a break-glass account is additive, not a fix to the underlying MSA problem. Whether to leave the MSA identity as a daily-driver admin alongside the break-glass account, restrict what it can do, or eventually retire it from the role entirely is a separate decision, not addressed here because it wasn't what was asked.
- **Resolved: MFA on the break-glass account is independently confirmed**, not just Raymond's statement — see Remediation.
- **The Security Defaults / MFA tension flagged before creation is still unresolved, and is now a confirmed live constraint rather than a hypothetical.** The break-glass account's only MFA method is a Microsoft Authenticator app tied to a specific iPhone — precisely the kind of single-device dependency break-glass guidance usually warns against, present here because Entra Free's Security Defaults doesn't support excluding this account from MFA. If that phone is ever unavailable, so is the break-glass path. Worth revisiting (a second, differently-anchored method — a FIDO2 key, printed recovery codes) once/if a Conditional Access tier is available, or sooner if it's cheap to do now.
- **Only one break-glass account exists, not Microsoft's enterprise-recommended two.** A deliberate lab-scale call stated in this exercise, not an oversight — revisit if the stakes here ever change.
- **Whether the MSA restriction would block Entra Connect itself, or only interactive Graph/portal queries, is untested.** Connect authenticates differently (typically a dedicated sync account, not the interactive admin identity), so this may be a non-issue for the sync work ahead — or it may not. Worth confirming before the member-server build, not after.
- **The `/users` malformed-response anomaly (a `200`-shaped envelope with a buried error) is filed but not reproduced.** One capture exists; a second identical query returned a clean `400` instead. Whether it's a rare race condition or something more systematic in how Graph's gateway layer handles this specific MSA/directory failure mode is unknown.
- **Neither `pwsh` nor `az` is installed on the Mac this session runs from.** Every tenant-side capture in this hybrid-identity thread will need either a browser-based Graph Explorer pass or a tooling install — not yet decided which.
- **The Server 2022 member server for Entra Connect has not been built.** Chosen over installing Connect on DC01 itself (correct practice, and a common interview probe), but it's a real VM build, not yet started, and needs an ISO source confirmed on the Proxmox host first.
- **Why the gateway and forwarder were misconfigured this way in the first place is not established.** Both are plausibly artifacts of the October build (the same build this skill's capture contract already flags as having an unreliable audit trail), but nothing in this exercise traces either misconfiguration to a specific cause — flagged as inherited-and-unexplained rather than assumed.
