Retrieval: a genuine Claude error, not a box behavior.

Three attempts to retrieve the certificate to a file, in order:

1. `qm guest exec 107 -- certreq.exe -retrieve -config "..." 7 "C:\issued-7.cer"` (bare, properly
   quoted). Reported "Certificate retrieved(Issued) Issued", exit 0. Immediate follow-up
   `certutil -dump -v C:\issued-7.cer` reported ERROR_FILE_NOT_FOUND.
2. Re-ran the retrieve wrapped in `powershell.exe -NonInteractive -Command '...'`, matching the
   pattern that worked for request 5 in evidence/48. This attempt timed out at 60 seconds and
   orphaned pid 3108 on CA01. `Get-Process -Id 3108` afterward showed 0.125 CPU seconds and no TCP
   connections — idle, not actively hung on network I/O.
3. A direct `Get-Item C:\issued-7.cer` (inside a single-quoted PowerShell command) found the file:
   2834 bytes, created 9/8/2026 11:28:50 PM — earlier than pid 3108's own start time of
   9/8/2026 11:30:08 PM. The file came from attempt 1, not attempt 2.

Root cause, found by re-reading the actual command sent for `-dump`:
`qm guest exec 107 -- certutil.exe -dump -v C:\issued-7.cer` — the Windows path was **not quoted**
in the bash command. Outside quotes, bash treats `\` as an escape character: `\i` in
`C:\issued-7.cer` becomes a literal `i`, so certutil received the argument `C:issued-7.cer` — a
path relative to certutil's own working directory on drive C, not the file at the drive root.
certutil correctly reported that path missing. The file was present at `C:\issued-7.cer` the whole
time. Every bare `certutil.exe` call against this path failed the same way until the path was
quoted (`"C:\issued-7.cer"`), matching the quoting evidence/49 already used for request 5's
retrieval. Attempt 2's orphaned process (pid 3108) is a separate, real finding — `certreq -retrieve`
run a second time against an already-retrieved request ID appears to hang under `qm guest exec`,
cause not established — but it did not prevent this thread from closing, since attempt 1's file
was valid throughout.
