--------------------------------------------------------------------------------
Correction, added the same session
--------------------------------------------------------------------------------

The two certutil command lines above are recorded as typed. They are not what executed.
Both pass C:\c2\issuing-ca.cer unquoted at the bash level, and bash consumes the
backslashes as escapes, so certutil received C:c2issuing-ca.cer, a drive-relative path.

The result is unaffected. -ca.cert wrote to the mangled path and -verify read the same
mangled path, so the chain output below describes the issuing CA certificate as intended.
The file C:\c2\issuing-ca.cer does not exist on CA01; that is how the defect surfaced,
in evidence/37, when jsmith ran the literal path at the console and got
ERROR_FILE_NOT_FOUND.

Do not cite this file for the existence of C:\c2\issuing-ca.cer.

--------------------------------------------------------------------------------
What this proves, and what it does not
--------------------------------------------------------------------------------

Proves:
- The chain builds from the issuing CA to the root, and the root element carries
  dwErrorStatus=0. Trust, time validity and key match are all correct.
- REVOCATION_STATUS_UNKNOWN (0x40) is the ONLY error status on the chain, at every
  level: ChainContext, SimpleChain, and the issuing CA element.
- Neither certificate carries an AIA, CDP or OCSP URL. The failure is the absence of
  revocation information, not an unreachable endpoint. This is the direct, captured
  consequence of the no-CRL decision recorded 2026-09-05.
- The issuing CA certificate is valid 9/5/2026 3:14 PM to 9/4/2031 3:14 PM. The root
  is valid 9/5/2026 2:16 PM to 9/2/2036 2:16 PM.

Does NOT prove:
- That REVOCATION_STATUS_UNKNOWN is what makes the enrollment UI hide the template.
  The enrollment failure is a client-side view held by jsmith at CA01's console. No
  capture in this repository holds it. The causal link is a hypothesis.
