## What this proves

`district.localClientAuthentication` is the first entry in the CA's issuance list. The
`certificateTemplates` attribute on the Enrollment Services object already holds the template.
The CA is configured to issue it. List membership is read from CA configuration and does not
depend on the caller's identity, so this reading stands regardless of the context below.

## What this does not prove

The twelve "Access is denied" results describe the calling identity, not `jsmith`.
`qm guest exec` runs as LocalSystem, which authenticates to AD as the computer account `CA01$`.

The output proves the caller internally. The `Computer` template returns
`Auto-Enroll: Access is denied`, while every other template returns a bare `Access is denied`.
That difference means Enroll passed on `Computer` and failed everywhere else. `CA01$` belongs to
Domain Computers, which holds Enroll on the `Computer` template. The remaining templates grant
Enroll to Domain Users, and a computer account is not a member. The results are what `CA01$`
should see.

No conclusion about `jsmith`'s enrollment rights can be drawn from this file. Reading these
lines as a rights finding for `jsmith` would be an error.
