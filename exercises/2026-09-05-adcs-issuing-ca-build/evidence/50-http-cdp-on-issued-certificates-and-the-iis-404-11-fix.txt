This is a documented AD CS and IIS interaction: a CRL filename carrying the DeltaCRLAllowed `+`
trips IIS's default double-escaping guard when combined with the space-containing CA name in the
same path segment. Not a misconfiguration introduced this session; a collision between two
Microsoft defaults.

--------------------------------------------------------------------------------
Consultation: fixed literal filename (Option A) vs. allowDoubleEscaping="true" on the IIS /pki
path (Option B, Microsoft's own commonly cited workaround for this exact error).
Raymond: "go with option A and we document the reasoning against B."
Reasoning against B, for the record: allowDoubleEscaping disables a request-filtering guard
against a real attack class (a double-encoded path segment hiding a second, malicious decode)
for every request under /pki, not only for this one filename. Option A costs a permanent small
step (rename on every copy); Option B costs a permanent gap in one guard rail to avoid that step.
No queued exercise needs delta CRL's default naming preserved on this one HTTP path, so nothing
is lost by choosing A.
