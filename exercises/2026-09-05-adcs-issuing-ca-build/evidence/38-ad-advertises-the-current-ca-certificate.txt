# AD advertises the current CA certificate, not a stale one

Disproves a hypothesis Claude raised in session 2026-09-07: that the pKIEnrollmentService
object in AD held a CA certificate different from the one CertSvc runs, which would explain
"a valid certification authority (CA) ... cannot be located". It does not. The thumbprint and
serial match exactly.

The hypothesis was raised because CertEnroll holds three .crt files with two distinct
timestamps (evidence/37), showing the CA certificate was installed more than once.

That run still carries two facts: dNSHostName is CA01.district.local, and cACertificate holds
exactly one value. Get-ADObject returns a multi-valued attribute as an
ADPropertyValueCollection; index it and cast, [byte[]]$o.cACertificate[0].

--------------------------------------------------------------------------------
What this proves
--------------------------------------------------------------------------------

- The pKIEnrollmentService object names CA01.district.local and holds exactly one
  cACertificate value.
- That certificate's thumbprint, 286C3546968D71398DE9C5276A4192039605454A, and serial,
  098A6109D790919464DF8F1D8BD96EBCE56CDC08, match the running CA certificate read in
  evidence/32 and the NTAuth entry read in evidence/33. All three agree.
- certificateTemplates holds 12 values, matching the 12-entry issuance list captured in
  evidence/29.
- A stale CA certificate in AD is not the cause of the enrollment failure.
