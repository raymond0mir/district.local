--------------------------------------------------------------------------------
Decoding the flag, against documentation
--------------------------------------------------------------------------------

-1509949440 as an unsigned 32-bit value is 2785017856, which is 0xA6000000.

Bit names and values from Microsoft Learn, X509CertificateTemplateSubjectNameFlag
enumeration (certenroll.h). Documentation, not a lab capture:

  0x80000000  SubjectNameRequireDirectoryPath
  0x20000000  SubjectNameRequireEmail
  0x04000000  SubjectAlternativeNameRequireEmail
  0x02000000  SubjectAlternativeNameRequireUPN

0xA6000000 is exactly those four bits. Two of them require the e-mail attribute. jsmith's
mail attribute is empty, so the CA's policy module denies the request.

Both templates hold the identical value. The client-auth template is schema version 4 and
User is schema version 1, so duplication changed the schema version and carried the name
flags across unaltered. The e-mail requirement was inherited, not chosen.

This also explains why the built-in User template appeared Unavailable for jsmith. Same flag
value, same empty attribute, same denial. The failure looked CA-wide because two templates
shared one requirement.

--------------------------------------------------------------------------------
The change, and Raymond's decision
--------------------------------------------------------------------------------

Asked on 2026-09-08 whether to change the template or populate mail on the user objects,
Raymond chose the template change: "good lets go with the template change".

Target value 0xA6000000 minus 0x20000000 minus 0x04000000 = 0x82000000, which is
-2113929216 signed. That keeps SubjectNameRequireDirectoryPath and
SubjectAlternativeNameRequireUPN. Entra CBA binds on SAN Principal Name to
userPrincipalName by default, so UPN is the binding that matters.

--------------------------------------------------------------------------------
What this proves
--------------------------------------------------------------------------------

- The enrollment failure had two independent causes, stacked. The first hid the second.
- Cause 1, now fixed: the template required the e-mail attribute in both the subject and
  the SAN, inherited verbatim from the built-in User template by duplication, and no user
  in district.local has mail populated. Error 0x80094812
  CERTSRV_E_SUBJECT_EMAIL_REQUIRED, request 4.
- Cause 2, now blocking: the CA cannot check revocation on its own chain while constructing
  a certificate. Error 0x80092012 CRYPT_E_NO_REVOCATION_CHECK, request 5. This is the same
  error code captured in evidence/32 at the chain-inspection stage, now appearing at the
  issuance stage.
- evidence/32's finding is promoted. It was recorded as real but not the enrollment blocker.
  That was correct at the time, because the e-mail requirement failed first. It is the
  blocker now.
- Requests 4 and 5 both reached the CA and both received policy-module verdicts, so nothing
  in the trust, rights, publication or reachability chain was ever broken.

--------------------------------------------------------------------------------
What this does not prove
--------------------------------------------------------------------------------

Whether cause 2 is the last one. Request 5 failed while constructing the certificate, so no
stage after that has been exercised.
