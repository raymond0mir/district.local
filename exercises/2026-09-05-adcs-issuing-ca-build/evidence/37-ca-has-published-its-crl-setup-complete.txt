--------------------------------------------------------------------------------
What this proves
--------------------------------------------------------------------------------

- SetupStatus is 1, SETUP_SERVER_FLAG only. Evidence/24 captured 769 immediately after
  -installcert. SETUP_FORCECRL_FLAG is no longer set.
- The CA has published a base CRL, "district.local Issuing CA.crl", 1220 bytes, and a
  delta CRL, "district.local Issuing CA+.crl", 1013 bytes, both at 9/7/2026 7:20:50 AM.
- CRLPublicationURLs holds four entries including an LDAP CDP with CSURL_SERVERPUBLISH,
  CSURL_ADDTOCERTCDP, CSURL_ADDTOFRESHESTCRL and CSURL_ADDTOCRLCDP.
- CACertPublicationURLs holds four entries including an LDAP AIA with CSURL_SERVERPUBLISH
  and CSURL_ADDTOCERTCDP.
- The CA's own CRL state is therefore not the cause of the enrollment failure.

--------------------------------------------------------------------------------
A defect in Claude's own commands, found by this read
--------------------------------------------------------------------------------

jsmith's console command used the literal path C:\c2\issuing-ca.cer and returned
ERROR_FILE_NOT_FOUND. That file does not exist. The cause is Claude's earlier command,
not the guest.

    qm guest exec 107 --timeout 90 -- certutil.exe -ca.cert C:\c2\issuing-ca.cer

The path is unquoted at the bash level. Bash consumes the backslashes as escapes and
passes C:c2issuing-ca.cer, a drive-relative path. certutil wrote there and reported
success. The -verify command in evidence/32 carried the identical mangling, so it read
the same file that -ca.cert wrote. Evidence/32's chain output is genuine and its
conclusion holds. The path recorded in evidence/32 is not the path that executed. A
correction note is written into that file.

Standing rule added to references/gotchas.md: quote Windows paths passed through
qm guest exec at the bash level.
